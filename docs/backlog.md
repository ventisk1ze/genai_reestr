# Бэклог реестра задач ЦК

Ведёт тимлид. Статусы: новая → в работе → на проверке у пользователя → принята.

## T-001. Каркас тестов и регрессия
- **Цель:** надёжный набор автотестов, на который опирается вся дальнейшая разработка.
- **Критерии приёмки:**
  1. Общий каркас в `tests/`: сервер во временной папке, мок шлюза модели, фейковый `gigacode`, остановка по PID.
  2. Тесты по API: создание и правка задачи, конфликт версий, справочники, карточки БЗ, удаление.
  3. Режимы хранилища: json и sqlite; перенос `copy-to` между ними.
  4. Ассистент: режим API через мок, режим GigaCode через фейковый CLI (аргументы, stdin, очистка ANSI).
  5. Регрессия на «уроки» из CLAUDE.md, которые проверяются без браузера.
  6. Ворота качества зелёные.
- **Статус:** новая

## T-002. Сотрудники, команды, PIN и админ-панель
- **Цель:** у каждого сотрудника свой PIN; сервер знает, кто действует; владелец ведёт людей, команды и лидов в простой админ-панели.
- **Критерии приёмки:**
  1. Справочник людей: ФИО, email, роль (сотрудник / тимлид), команда (тимлид команды), признак «активен».
  2. PIN у каждого сотрудника, задаёт и сбрасывает админ в админ-панели. Хранится только хеш с солью (PBKDF2, `hashlib`), сам PIN — нигде; посмотреть PIN нельзя, только задать новый.
  3. Вход: страница просит ФИО и PIN; сервер выдаёт сессию (в памяти сервера, в браузере — только в памяти вкладки). 5 неверных попыток — пауза 5 минут для этого ФИО. Выход — кнопкой.
  4. Любая запись (`POST`/`DELETE /api/*`) — только с сессией; автор действия берётся из сессии, а не из `X-User`. Чтение без сессии доступно (команды GigaCode `ctx`, `tasks`, `task`).
  5. Админ — владелец сервера: админский PIN вводится при каждом запуске `start.sh` и передаётся в `app.py` через stdin, нигде не хранится.
  6. Админ-панель (только для админа): люди и PIN, команды и лиды, справочники (переезжают сюда из общего раздела), правка любой задачи и любого поля, включая статус, с записью в историю.
  7. Контракт API обновлён во фронтенде, командах GigaCode и README; ворота качества зелёные; тесты на вход, блокировку, запрет записи без сессии, админские права.
- **Допущения:** хранение хеша PIN — осознанное исключение из правила 1 (решение пользователя: PIN у каждого, задаёт админ). После перезапуска сервера все входят заново. `create-task` из GigaCode требует PIN тимлида с терминала; в лава-болле (без терминала) создание задачи — через веб-форму. Права по этапам — в T-003.
- **Решения в работе:** админ входит переключателем «Войти как администратор», в истории — «Администратор»; без входа — только форма входа; справочники видит и правит только админ (вкладка переехала в админ-панель); переименование сбрасывает PIN (с предупреждением в форме); сессия — только в памяти вкладки, перезагрузка = вход заново; PIN — только цифры 0–9; `REG_ENV_FILE` ("" — не читать registry.env) для тестов. Исключение из правила 1 записано в CLAUDE.md.
- **Ветка:** `feature/T-002-pin-admin`. Тесты: 73 (tests/helpers.py, test_t002*, test_smoke, test_lessons).
- **Проверить на DataLab:** `start.sh` целиком (ввод PIN, `/proc/<pid>/environ` и `cmdline` без PIN и пароля GP); хеши в таблице config в GP; вход коллеги через connect.sh и jupyter-server-proxy (проходит ли `X-Session`); `create-task` в терминале GigaCode (есть ли /dev/tty); лава-болл не просит PIN.
- **Замечено, вне рамок:** история диалога лава-болла хранится в localStorage браузера — на общем компьютере её увидит следующий вошедший; DELETE задачи доступен любому вошедшему (ограничить в T-003).
- **Статус:** принята (2026-10-19), слита в main

## T-003. Жизненный цикл со статусом «Согласована» и права по этапам
- **Цель:** каждый участник видит и меняет в карточке только своё и только на своём этапе.
- **Порядок:** Новая → В работе → На согласовании (⇄ На доработке) → Согласована → Завершена → Принята.
  - Тимлид-автор: постановка в «Новая»; на согласовании — согласовать или вернуть на доработку, решение «сохранять в БЗ»; в «Завершена» — проверить БЗ и перевести в «Принята» или вернуть.
  - Исполнитель (и замещающий): взять в работу; блок «Результат» в «В работе»/«На доработке»; блок «База знаний» в «Согласована» → «Завершена». Если БЗ «нет» — шаг БЗ пропускается.
  - «Принята» ставит тимлид. Закрытые задачи правит только админ.
- **Критерии приёмки:**
  1. Статус «Согласована» во всех местах: реестр, доска, фильтры, рельса этапов, цвета, отчёты.
  2. Сервер проверяет каждое сохранение задачи: допустим ли переход статуса для этого пользователя и меняются ли только поля, разрешённые ему на этом этапе. Нарушение → 403 с понятным текстом; проверка атомарна с проверкой версии.
  3. Создавать задачи может тимлид (тимлид задачи = он сам) и админ.
  4. Карточки БЗ сохраняет исполнитель/замещающий в «Согласована» (и админ).
  5. Удаление задачи — только админ.
  6. Интерфейс показывает только доступные кнопки и делает недоступные поля только для чтения.
  7. Письма по шаблонам под новый порядок; README и skills обновлены; ворота зелёные; тесты на матрицу прав.
- **Допущения:** «тимлид-автор» = поле `teamlead` задачи; права у тимлида только на задачи, где он `teamlead`. Исполнитель и замещающий равноправны. Старые задачи не мигрируются: «Завершена» и «Принята» трактуются по-новому. Автоматический шаг «Запросить карточку БЗ» у ответственного за БЗ убирается из потока (карточки делает исполнитель); письмо «Сформировать карточку(ки)» остаётся в меню писем. Новое письмо исполнителю при согласовании — тема `{ID}_Согласована`. У регулярных задач: обратная связь и «Новый цикл» — тимлид, новый цикл — после «Принята».
- **Решения в работе:** клиент шлёт код действия (`action_code` + `params`), статус и служебные поля ставит сервер, подделка служебных полей игнорируется; сервер сам требует исполнителя и срок при создании; кнопка «Взять в доработку» убрана — из «На доработке» исполнитель сразу правит результат и отправляет на согласование (подсказка с замечанием тимлида видна всем); «Новый цикл» уносит в архив и карточки; действие не из того статуса — 403; админ выполняет любое действие этапа. Писем стало семь: новые «Согласована» (исполнителю) и «Принята» (руководителю ЦК, бывшее «Завершена»); «Завершена» теперь тимлиду.
- **Ветка:** `feature/T-003-stages`. Тесты: 133 (новый test_t003.py — 60).
- **После приёмки (решение пользователя):** темы писем `_Согласована` и `_Принята` оставлены, вернуться по опыту использования.
- **Известное ограничение:** права на карточку БЗ проверяются до её записи, не атомарно с ней (гонка маловероятна).
- **Проверить на DataLab:** права вместе с проверкой версии на GP (откат при 403); карточки БЗ на GP; два сервера тимлидов на одной базе; кнопки и поля «только чтение» через jupyter-server-proxy в VDI; новые письма в почтовом клиенте (тема `_Согласована`, длина mailto); `create-task` с обязательными исполнителем и сроком в терминале GigaCode.
- **Статус:** принята (2026-10-19), слита в main

## T-004. Фильтр по умолчанию: мои задачи / реестр тимлида
- **Цель:** после входа сотрудник сразу видит свои задачи, тимлид — свой реестр; переключиться на все задачи можно одним кликом.
- **Критерии приёмки:**
  1. В панели фильтров реестра и доски есть переключатель охвата «Мои | Все» (у тимлида — «Мой реестр | Все»), у каждого варианта — число задач.
  2. Сотрудник после входа видит «Мои»: задачи, где он исполнитель или замещающий.
  3. Тимлид после входа видит «Мой реестр»: задачи, где он тимлид, плюс задачи, где он исполнитель или замещающий.
  4. Админ после входа видит все задачи, переключателя нет.
  5. Охват сбрасывается на значение по умолчанию при каждом входе: следующий вошедший на этом компьютере не получает чужой выбор. Остальные фильтры работают как раньше.
  6. Если в выбранном охвате задач нет, вместо пустой таблицы — «Ваших задач нет» и кнопка «Показать все».
  7. Флажок «Мои» убран — его заменяет переключатель. Счётчики на чипах статусов учитывают охват.
- **Допущения:** «реестр тимлида» — задачи, где он указан тимлидом (а не все задачи его сотрудников у других тимлидов); свои задачи как исполнителя тимлид тоже видит. Охват не хранится в localStorage. Доклады и база знаний охватом не фильтруются. Только фронтенд, контракт API не меняется.
- **Решения в работе:** «Ваших задач нет» — только когда своих задач нет совсем; если они скрыты другими фильтрами — «Задач по этим фильтрам нет» с кнопкой «Показать все». Число задач на переключателе — с учётом остальных фильтров, кроме статуса. Старый сохранённый флажок «Мои» игнорируется.
- **Ветка:** `feature/T-004-default-filter`. Тесты: 151 (новый test_t004.py — 18). Проверено в браузере: сотрудник (в т. ч. как замещающий), тимлид, админ, смена пользователя, оба пустых состояния, доска.
- **Проверить на DataLab:** открыть через `…/proxy/39246` без слеша, войти сотрудником и тимлидом; вид переключателя в VDI.
- **Статус:** принята (2026-10-19), слита в main

## T-005. Вход переживает перезагрузку страницы
- **Цель:** после F5 сотрудник остаётся в системе и не вводит PIN заново.
- **Решение пользователя:** сессия — в хранилище вкладки (sessionStorage): переживает перезагрузку, в новой вкладке и после закрытия вкладки — вход заново. Осознанное исключение из правила 1 (идентификатор сессии в браузере; сам PIN — нигде).
- **Критерии приёмки:**
  1. После входа и F5 пользователь в системе: та же роль, тот же охват «Мои»/«Мой реестр», PIN не спрашивается.
  2. При загрузке страницы сохранённая сессия проверяется на сервере (`/api/whoami`); недействительная (истекла, перезапуск сервера, сотрудник деактивирован) — стирается, показывается форма входа.
  3. «Выйти» и ответ 401 стирают сессию из хранилища вкладки.
  4. В localStorage сессии нет; PIN не сохраняется нигде.
  5. Админ тоже переживает F5.
- **Допущения:** хранится только идентификатор сессии; данные пользователя берутся с сервера. Срок жизни — как у сессии на сервере (12 ч).
- **Решения в работе:** при загрузке страницы сохранённая сессия проверяется через `/api/whoami` до загрузки реестра (форма входа не мигает); если сервер недоступен, ключ не стирается. Тест T-002 про хранение сессии обновлён: в sessionStorage разрешён только ключ `ck.session`.
- **Ветка:** `feature/T-005-tab-session`. Тесты: 172 (новый test_t005.py — 21).
- **Проверить на DataLab:** доступен ли sessionStorage в браузере VDI (если нет — после F5 снова спросит PIN, как раньше); F5 через `…/proxy/39246`.
- **Статус:** принята (2026-10-19), слита в main

## T-006. История лава-болла у сотрудника и история запросов
- **Цель:** история диалога с помощником привязана к сотруднику и хранится на сервере; список прошлых запросов, чтобы задать их снова.
- **Решения пользователя:** хранение на сервере (json / sqlite / GP); «история поиска» — это прошлые запросы к лава-боллу.
- **Критерии приёмки:**
  1. Диалог каждого сотрудника хранится на сервере отдельно; после входа на любом компьютере он видит свой диалог, другой сотрудник его не видит (ни в интерфейсе, ни через API).
  2. В localStorage диалога нет; старый ключ `ck.ai.msgs` удаляется. При выходе диалог исчезает с экрана.
  3. Список «История запросов» в окне помощника: последние запросы сотрудника (до 30, без повторов, новые сверху); клик подставляет текст в поле ввода, не отправляя.
  4. «Новый диалог» очищает диалог, но не историю запросов; историю запросов можно очистить отдельно.
  5. Работает во всех трёх хранилищах; в GP — новая таблица с `DISTRIBUTED BY`, без `ON CONFLICT`.
  6. Без сессии — 401; контракт новых путей описан в README.
- **Допущения:** хранятся последние 40 сообщений диалога; ошибки не сохраняются. История не переносится командой копирования хранилищ. Команды GigaCode не меняются.
- **Решения в работе:** история сохраняется из исходных сообщений запроса, а не из урезанных до 30 для модели — лимит 40 достижим. Сохраняет обёртка `/api/llm` после ответа (оба движка); сбой записи истории не отнимает ответ у пользователя. Кнопка истории запросов — значок часов в шапке помощника; Esc и клик мимо закрывают список.
- **Ветка:** `feature/T-006-ai-history` (поверх T-005). Тесты: 220 (новый test_t006.py — 48). Проверено в браузере с моком модели: запросы без повторов, клик подставляет текст, F5 — диалог на месте, «Новый диалог» не трогает запросы, очистка запросов, выход и вход другим сотрудником — чужого нет, старый `ck.ai.msgs` удаляется.
- **Проверить на DataLab:** режим gp — создание таблицы `ai_history` в GP6 и перезапись (delete+insert); лава-болл через настоящий шлюз и GigaCode; диалог с другого компьютера через connect.sh.
- **Статус:** принята (2026-10-19), слита в main

## T-007. Команды: тимлид и заместитель, права по команде
- **Цель:** админ создаёт команды и назначает тимлида и заместителя; права тимлида действуют на задачи своей команды; у заместителя те же права, что у лида.
- **Решения пользователя:** в поле «Тимлид» задачи записывается тот, кто поставил задачу (лид или зам), письма «тимлиду» идут ему; права на задачу — у лида и зама команды задачи.
- **Критерии приёмки:**
  1. В справочнике появляются команды `teams: [{id, name, lead, deputy}]`; `id` стабилен (переименование команды не ломает задачи). Состав — `people[].team = id команды`, одна команда на человека.
  2. Админ-панель: создать, переименовать, удалить команду; выбрать лида и зама из активных сотрудников; видно состав; сотрудника можно перевести в другую команду. Удалить команду, у которой есть задачи, нельзя — понятное сообщение.
  3. У задачи появляется поле `team`. При создании — команда автора (лид или зам); если автор руководит несколькими командами — выбирает в форме. Поле «Тимлид» = автор.
  4. Права тимлида из T-003 (постановка, согласование, приёмка, возврат, новый цикл, обратная связь) — у лида и зама команды задачи; сервер проверяет по команде. Создавать задачи могут лиды, замы и админ.
  5. «Мой реестр» (T-004) у лида и зама — задачи их команды плюс свои как исполнителя.
  6. Миграция без потерь: существующий справочник без `teams` превращается в команды по нынешним тимлидам (название — ФИО лида, состав — как сейчас); у старых задач команда определяется по полю «Тимлид». Ни одна старая задача не теряет тимлида.
  7. `/api/whoami` и `/api/login` отдают, в каких командах пользователь лид или зам; GigaCode `ctx` показывает команды; `create-task --by` принимает зама; при нескольких командах — `--team`.
  8. Работает во всех хранилищах (команды — в справочнике, новых таблиц нет).
- **Допущения:** роль «сотрудник/тимлид» в карточке человека больше не задаётся вручную — она следует из команд. Матрица блоков не меняется. Фильтр «Все тимлиды» остаётся.
- **Решения в работе:** id мигрированных команд — t1, t2… по порядку тимлидов; человек с командой без тимлида даёт команду без лида (состав не теряется). Старая задача получает команду по полю «Тимлид» (лид, затем зам) и записывает её при первой правке; если тимлид не руководит ни одной командой — права по полю «Тимлид», как раньше. Сохранение справочника без `teams` оставляет сохранённые команды (дефект, найденный qa). При нескольких командах без выбора — 400, чужая команда — 403. `team` меняет только админ. Права зама действуют сразу после сохранения справочника, без повторного входа.
- **Ветка:** `feature/T-007-teams`. Тесты: 295 (новый test_t007.py — 75; старые тесты переведены на явные команды). Проверено в браузере: миграция старого реестра, блок «Команды», назначение зама, «Мой реестр» и правка задачи зама, отказ по чужой команде.
- **Проверить на DataLab:** миграция справочника в GP (первое сохранение пишет teams); `create-task --by <зам> [--team]` в терминале GigaCode; вид блока «Команды» в VDI — ФИО в узких селектах обрезаются.
- **Статус:** принята (2026-10-19), слита в main

## T-008. Помощник: скиллы по ролям, результат и карточка знаний
- **Цель:** «Постановка задачи» — только лиду, заму и админу; новый скилл для исполнителя и тимлида — описать результат и собрать карточку знаний, перенести их в задачу кнопкой; починить шапку и тексты помощника.
- **Решения пользователя:** новый скилл покрывает и результат («В работе», «На доработке»), и карточку знаний («Согласована»); в задачу всё попадает кнопкой под ответом, не автоматически.
- **Критерии приёмки:**
  1. Доступ к скиллу задаётся в SKILL.md; сервер не даёт запустить недоступный скилл (403 по-русски), список скиллов в помощнике — только доступные. По умолчанию: у лида и зама — «Постановка задачи», у сотрудника — новый скилл.
  2. Помощник знает, кто пишет (ФИО, лид/зам какой команды или сотрудник), и видит его задачи (номер, название, статус, его роль в задаче).
  3. Новый скилл: человек называет номер задачи; помощник сверяет, что он исполнитель или замещающий (тимлиду задачи — подсказывает, но результат и карточку переносит исполнитель). «В работе»/«На доработке» — помогает сформулировать результат, кнопка «Перенести результат в задачу N» открывает задачу с заполненными полями результата. «Согласована» — собирает карточку знаний, кнопка «Прикрепить карточку к задаче N». Другие статусы — объясняет, что дальше.
  4. Кнопка недоступна (с пояснением), если пользователь не исполнитель/замещающий или статус не тот; сервер проверяет права как в T-003.
  5. Шапка: название скилла не обрезается, списки не переносятся на вторую строку при обычной ширине окна; заголовок «Помощник» без «тимлида»; приветствие и примеры — свои у каждого скилла; кнопка «доработать постановку» — только тимлиду задачи.
  6. В режиме GigaCode реплики подписаны ролью пишущего, а не всегда «Тимлид».
- **Решения в работе:** новый скилл `rezultat` («Результат и карточка знаний»), доступен всем; тимлиду задачи даёт подсказки без блоков переноса. Поля frontmatter: `roles`, `greeting`, `examples`, `placeholder`; сотруднику по умолчанию — `REG_DEFAULT_SKILL_EMPLOYEE` (rezultat). Без входа `GET /api/llm` отдаёт только общедоступные скиллы. Неизвестный скилл — 400 без подмены. Контекст модели: до 50 задач пишущего, принятые — за 30 дней; исполнителю в рабочих статусах — описание, текущий результат и замечание тимлида (до 400 символов). Несколько блоков в ответе — несколько кнопок. «Новый диалог» стал значком; селекты скилла и движка — отдельной строкой. Заодно расширены селекты команды в админке.
- **Ветка:** `feature/T-008-assistant` (поверх T-007). Тесты: 342 (новый test_t008.py — 47). Проверено в браузере с моком модели: у сотрудника только новый скилл и его приветствие; «Перенести результат в задачу 2» открыла задачу с заполненными полями без сохранения; «Прикрепить карточку к задаче 1» прикрепила карточку; у тимлида оба скилла, кнопка карточки неактивна с причиной; в контексте модели — кто пишет и его задачи.
- **Проверить на DataLab:** выдают ли настоящий шлюз и GigaCode блоки `result`/`card` в нужном формате (особенно `\n` в тексте карточки); вид шапки помощника в VDI; длина контекста при 50 задачах.
- **Статус:** принята (2026-10-19), слита в main

## T-009. Файлы .docx и .txt в помощнике
- **Цель:** сотрудник прикладывает к сообщению помощнику документы .docx и .txt; их текст уходит модели в контексте вместе с запросом.
- **Критерии приёмки:**
  1. В окне помощника — кнопка «Приложить файл» (скрепка) у поля ввода и перетаскивание файла в окно; к одному сообщению — до 5 файлов. Над полем ввода — плашки файлов: имя, объём текста, пометка «обрезан», крестик «убрать». Сообщение можно отправить и без текста, только с файлами.
  2. Форматы — .docx и .txt; текст извлекает сервер реестра на стандартной библиотеке: .docx — абзацы, списки, таблицы (ячейки через « | »); .txt — UTF-8 (с BOM и без), UTF-16 с BOM, иначе cp1251; переводы строк Windows → `\n`. Другой формат (.doc, .pdf…), повреждённый или пустой файл — понятная ошибка по-русски при прикреплении.
  3. Текст файлов уходит модели вместе с сообщением в обоих режимах (API и GigaCode), с явной разметкой «Файл «имя»» отдельно от текста сообщения; в пузыре сообщения — имена файлов, а не их текст.
  4. Приложенное остаётся в контексте диалога: на следующие вопросы помощник отвечает с учётом документа. Диалог с файлами хранится на сервере, как в T-006: после F5 и на другом компьютере плашки на месте; «Новый диалог» убирает и их. В «Истории запросов» — только текст запроса.
  5. Лимиты (registry.env, по умолчанию): файл — до 10 МБ; текст одного файла — до 50 000 символов, длиннее — обрезается с пометкой для модели и на плашке; текст всех файлов диалога в запросе к модели и в сохранённой истории — до 100 000 символов, считая от новых к старым, что не влезло — остаётся имя файла с пометкой «текст не передаётся». Лимиты применяет сервер, клиенту не доверяет.
  6. Безопасность: файлы на диск не пишутся (кроме истории диалога); zip-бомба и XML с DOCTYPE отклоняются; без сессии — 401.
  7. Контракт API — в README; ворота качества зелёные; тесты на извлечение, кодировки, ошибки, лимиты, передачу в оба движка и историю.
- **Допущения:** «агент» — помощник (лава-болл) в обоих режимах. PDF и старый .doc не поддерживаются: без новых зависимостей их не разобрать — ошибка с подсказкой сохранить как .docx. Текст файлов хранится в истории диалога на сервере вместе с диалогом (T-006) — каждый видит только своё.
- **Решения в работе:** .docx разбирается потоком (pyexpat), а не деревом ElementTree — дерево на «бомбе» из пустых абзацев занимало до 1 ГБ памяти (дефект, найденный qa). Zip-бомба — распаковка больше 50 МБ или больше 10 МБ при сжатии сильнее 100:1 (однообразные настоящие документы сжимаются до ~230:1 и проходят); вложенность XML больше 256 — отказ; файлы разбираются по одному, предела времени нет (худший случай — 2–5 с). Списки — только абзацы со своим `w:numPr`, нумерация из стилей не распознаётся (иначе нумерованные заголовки стали бы пунктами). Общий лимит — от новых сообщений к старым, внутри сообщения — по порядку файлов. Ответ `POST /api/llm` отдаёт `msgs` (диалог как сохранён), `GET /api/llm` — `file_limits`. Тосты теперь поверх окна помощника и закрываются кликом; ответ модели, пришедший после выхода, в диалог следующего вошедшего не попадает.
- **Ветка:** `feature/T-009-ai-files`. Тесты: 434 (новый test_t009.py — 92). Проверено в браузере с моком модели (dev и qa): скрепка и перетаскивание, плашки и «обрезан», ошибки форматов, отправка только файлов, F5 и повторный вход, пометка «текст не передаётся», «Новый диалог», имя файла с HTML не исполняется.
- **Проверить на DataLab:** файлы 5–10 МБ через jupyter-server-proxy и через прокси коллеги (тело до ~13,5 МБ base64, возможен 413); перетаскивание из проводника в VDI (запасной путь — скрепка); настоящие корпоративные .docx (списки из стилей, рецензирование, надписи) и .txt из «Блокнота»; шлюз и GigaCode с ~100 000 символов файлов (контекст, таймауты); json — `ai_history.json` перезаписывается целиком и может дорасти до нескольких МБ; gp — строки `ai_history` с текстом файлов.
- **Статус:** на проверке у пользователя

## T-010. Выгрузка карточек знаний в BB (Bitbucket) через MCP — из контейнера сотрудника
- **Цель:** исполнитель в «Согласована» одной кнопкой выгружает карточки знаний задачи в репозиторий БЗ в Bitbucket — веткой и pull request от своего имени; ссылка на PR попадает в задачу.
- **Решения пользователя:** ветка и pull request; выгружает исполнитель (или замещающий) в «Согласована»; только с учёткой самого сотрудника и из его контейнера: учётка сотрудника не попадает к владельцу сервера реестра, учётки владельца — к сотруднику. Предложение принято с умолчаниями: владелец, если сам исполнитель, выгружает через свой прокси (`bash connect.sh 127.0.0.1:39246`); в репозиторий — только файлы карточек в `KB/`, KB.json не трогаем.
- **Критерии приёмки:**
  1. В «Согласована» исполнитель или замещающий (и админ) видит в разделе «База знаний» задачи кнопку «Выгрузить карточки в BB», если есть хотя бы одна карточка. Нажатие (с подтверждением) создаёт в репозитории БЗ новую ветку с файлами карточек в папке `KB/` и pull request в целевую ветку — от имени сотрудника, с его учёткой. Ссылка на PR записывается в задачу: история, список выгрузок, «Факт размещения карточки» (пусто — заполняется, иначе ссылка дописывается). Повторная выгрузка — новая ветка и новый PR; если в BB карточки уже такие же — понятное сообщение, PR не создаётся.
  2. Выгрузку выполняет процесс реестра в контейнере сотрудника — прокси `connect.sh`: он сам обрабатывает `/api/bb/status` и `/api/bb/upload`, по сессии сотрудника берёт у сервера реестра права, карточки и настройки репозитория, запускает у себя MCP-сервер BB (stdio) и вызывает его инструменты; серверу реестра отдаёт только результат (ссылка на PR, ветка, файлы). Сервер реестра в BB не ходит; при обращении напрямую, без прокси, — понятный отказ «выгрузка — через свой прокси».
  3. Учётка BB: `connect.sh` при каждом запуске спрашивает логин и пароль BB (если задан MCP-сервер; Enter — без выгрузки) и передаёт прокси через канал на stdin; прокси передаёт их MCP-серверу по отдельному каналу в память процесса. Учётки нет нигде: ни в файлах, ни в аргументах, ни в окружении процессов прокси и MCP-сервера (`/proc/<pid>/environ`), ни в журналах и ответах API, ни на сервере владельца.
  4. Защита учётки на стороне сотрудника: адрес репозитория из настроек сервера реестра принимается, только если хост совпадает с корпоративным Bitbucket из настроек сотрудника, без логина в URL; имена файлов, папка и ветка проверяются, файлы пишутся только внутри временного клона; клон удаляется после выгрузки, в том числе при ошибке.
  5. Права проверяет сервер реестра: исполнитель или замещающий (и админ), «Согласована», есть карточки; иначе 403/400 с понятным текстом, MCP-сервер не запускается.
  6. Ошибки MCP-сервера и BB показываются по-русски, с шагом, на котором упало, без секретов; в задачу при ошибке ничего не пишется. Нет учётки или MCP-сервера у сотрудника, не настроен репозиторий у владельца — кнопка неактивна с пояснением, что настроить.
  7. Реестр — MCP-клиент на стандартной библиотеке, новых зависимостей нет. Настройки несекретные, в registry.env: у владельца `REG_BB_REPO_URL`, `REG_BB_PROJECT`, `REG_BB_REPO`, `REG_BB_BRANCH` (master), `REG_BB_DIR` (KB); у сотрудника `REG_BB_MCP` (путь к server.py), `REG_BB_MCP_PYTHON`, `REG_BB_BASE_URL` (корпоративный Bitbucket по умолчанию).
  8. Контракт API, connect.sh и настройки — в README; ворота зелёные; тесты с фейковым MCP-сервером и локальным git-репозиторием.
- **Допущения:** карточка в BB — файл `KB/<имя файла карточки в реестре>.md` в формате реестра (`# вопрос` + ответ). MCP-сервер — пользовательский server.py (инструменты `bitbucket_clone`, `bitbucket_checkout`, `bitbucket_add`, `bitbucket_status`, `bitbucket_commit`, `bitbucket_push`, `bitbucket_create_pull_request`), его пакеты — только у него. Админ выгружает с учёткой того, чей это прокси. server.py сам на время git-команды кладёт пароль во временный askpass-файл и в окружение процесса git — это вне реестра, правка предлагается пользователю отдельно.
- **Решения в работе:**
  - Выгрузку делает прокси сотрудника: `run_proxy` сам обрабатывает `GET /api/bb/status` и `POST /api/bb/upload`. У сервера — `/api/bb/status`, `/api/bb/task`, `/api/bb/done`; прямой upload на сервер — 400 «через свой прокси».
  - Учётка: `connect.sh` → stdin прокси (`--bb-creds-stdin`, канал — подстановка процесса с `exec`) → лаунчер MCP-сервера по отдельному fd (`pass_fds`) → `os.environ` уже запущенного процесса. Окружение MCP-сервера — без `BITBUCKET_USERNAME`/`BITBUCKET_PASSWORD`. Маска учётки в ошибках и журналах: как есть, URL- и JSON-кодирование, base64 `логин:пароль`, `…@` в адресах.
  - «Без изменений» сравнивается с целевой веткой: повтор до слияния первого PR даёт второй PR. Подтверждение предупреждает об этом и показывает прошлую выгрузку (правка по ревью). Вторая выгрузка на том же прокси, пока идёт первая, — 409.
  - Остановка MCP-сервера: закрыть stdin, 3 с, затем TERM/KILL его группе процессов (вместе с git).
  - `bb` — служебное поле (`F_SERVICE`, через `/api/task` не подделать); «Новый цикл» уносит его в архив вместе с карточками (`CYCLE_KEEP`). В ответы добавлены `missing`, `target`, `server_configured`, `by`, `step`.
  - `connect.sh` читает `registry.env` с той же проверкой на секреты, что `start.sh`, и останавливает старый прокси, только если по PID действительно `app.py proxy`.
- **Попутно — дефект прокси, найден qa, был до T-010; решение тимлида — чинить здесь:** прокси коллеги пересылал серверу владельца все заголовки браузера, включая куку JupyterHub сотрудника, `Authorization` и `X-XSRFToken`, а браузеру отдавал `Set-Cookie` владельца. Через куку владелец мог получить вход в Jupyter сотрудника — в контейнер, где прокси держит учётку BB. Теперь — белый список (`X-Token`, `X-Session`, `X-User`, `Content-Type`, `Accept`, `Accept-Language`), `Set-Cookie` в ответе не проходит. Старые проверки сужены по смыслу: в test_t009 `tempfile` разрешён только в `bb_upload`, в test_t002 — «сервер сам не ставит куки» вместо поиска слова Set-Cookie.
- **Ветка:** `feature/T-010-bb-mcp` (поверх T-009). Тесты: 544 (новые test_t010.py — 108, test_proxy_headers.py — 2; фейковый MCP-сервер — tests/fake_bb_mcp.py).
  - Стенд ревью с настоящим MCP SDK (mcp 2.3.0) и bitbucket-частью server.py пользователя: ветка, файл с кириллицей в `KB/`, PR с учёткой сотрудника, запись в задачу, «без изменений» после слияния; учётки нет в исходном окружении MCP-сервера (KERN_PROCARGS2), журналах и хранилище; клоны удалены.
  - dev проверил в браузере: подтверждение, «Выгружаю в BB…», тост «Открыть PR», список выгрузок, правку во время выгрузки без конфликта версий.
- **Пауза:** приостановлена 2026-10-23 по просьбе пользователя и 2026-10-26 из-за лимита — оба раза до первых правок. Продолжена 2026-10-26 по «ок» пользователя; он же дал «ок» на пуш веток T-009 и T-010.
- **Проверить на DataLab:**
  - настоящий server.py против настоящего Bitbucket: clone, push, PR через REST, SSL, сеть, тексты ошибок и подсказки;
  - `/proc/<pid>/environ` и cmdline прокси и MCP-сервера — учётки BB нет;
  - `connect.sh` в терминале: скрытый ввод пароля, setsid, pgrep, подстановка процесса, в PID-файле — python прокси;
  - пересылает ли jupyter-server-proxy куку JupyterHub; работает ли `/proxy/9000` (и без слеша) с белым списком заголовков; таймаут jupyter-server-proxy на выгрузке до 600 с;

## R-001. Рефакторинг: FastAPI-бэкенд в пакете registry/, фронтенд — шаблон + модули
- **Цель:** код читаем и правится людьми: бэкенд — FastAPI, разбитый на слои; фронтенд — конвенциональная раскладка static/ вместо одного файла. Поведение — бит-в-бит прежнее: контракт `/api/*` (пути, заголовки X-Token/X-Session, коды и тексты ошибок), CLI-флаги, сценарии start.sh/connect.sh — без изменений.
- **Решение пользователя:** FastAPI/uvicorn/jinja2 — осознанное исключение из правила «без новых зависимостей» (вопрос задавался до начала работ). По умолчанию приняты: зависимости через requirements.txt (вендоринг для DataLab — если внутренний PyPI недоступен), Jinja2 — только для каркаса страницы, ES-модули на фронте (без сборки).
