# Реестр задач ЦК — DataLab Pro

Веб-интерфейс реестра по регламенту ЦК плюс ИИ-ассистент. Скиллы ассистента — общие для веб-чата (API модели) и GigaCode.

```
app.py                     точка входа: python app.py … (её зовут start.sh, connect.sh, команды GigaCode и тесты)
registry/                  бэкенд-пакет (FastAPI), послойно:
  config.py                настройки: registry.env, переменные окружения, лимиты — всё в одном месте
  errors.py                исключения домена → HTTP-коды (маппинг — в api/)
  util.py                  помощники без состояния (время, JSON, пути карточек)
  runtime.py               изменяемое состояние процесса (хранилище, режим --local, порт)
  org.py                   справочник людей и команд (чистые функции)
  sessions.py / auth.py    сессии в памяти, вход по PIN (PBKDF2), админские операции
  store/                   хранилища: json_store.py, sqlite_store.py, gp_store.py (Greenplum/asyncpg)
  tasks.py                 жизненный цикл задачи и права по этапам (матрица — здесь)
  settings.py / cards.py   справочники и карточки знаний
  kb.py                    база знаний (T-012): права, цель из настроек, запись ссылки в карточку
  ai/                      ассистент: skills.py, context.py, files.py (.docx/.txt), llm.py (шлюз, GigaCode)
  bb/                      Bitbucket напрямую (git + REST): direct.py, ontology.py, upload.py (T-010),
                           kb.py — база знаний (T-012): онтология, отправка через постоянный клон
  proxy.py                 прокси коллеги (stdlib, без fastapi — работает в любом контейнере)
  cli.py                   команды для GigaCode (ctx, tasks, task, create-task)
  api/                     HTTP-слой FastAPI: роуты по доменам, маппинг ошибок, статика
  models.py                схемы тел запросов (pydantic) — декларация контракта /api/*
  server.py / main.py      запуск uvicorn и argparse
start.sh                   запуск общего реестра (у одного участника команды)
connect.sh                 подключение остальных участников к общему реестру
registry.env               несекретные настройки (по желанию, см. ниже)
requirements.txt           зависимости сервера: fastapi, uvicorn, jinja2 (для GP — ещё asyncpg)
templates/index.html       каркас интерфейса (Jinja2: сервер подставляет ключ API страницы)
static/css/*.css           стили по областям (порядок загрузки = порядок в файле-каркасе)
static/js/*.js, js/views/  интерфейс — ES-модули без сборки; вход — js/main.js
skills/<имя>/SKILL.md      скиллы — один источник для веба и GigaCode
data/                      реестр в режиме json (создаётся сам)
```

Зависимости: серверу владельца нужны `fastapi`, `uvicorn`, `jinja2` (`pip install --user -r requirements.txt`
из внутреннего PyPI; для `REG_STORAGE=gp` — ещё `asyncpg`). Прокси коллеги, команды GigaCode
и выгрузка в BB работают на стандартной библиотеке: fastapi в контейнере сотрудника не нужна.

## Как это устроено в команде

Реестр запускает **один** участник (владелец) — у него сервер и подключение к хранилищу. Остальные открывают тот же реестр через свой Jupyter: DataLab Pro пускает коллег к сервисам друг друга на портах 39235–39246 по адресу `http://jlab-<табельный>:<порт>`, а в браузер их выводит небольшой прокси.

```
браузер коллеги → его Jupyter /proxy/9000/ → прокси (connect.sh) → http://jlab-<табельный владельца>:39246 → сервер реестра → JSON / Greenplum
браузер владельца → его Jupyter /proxy/39246/ ──────────────────────────────────────────────↗
```

### Владелец: запустить общий реестр

```bash
cd ~/nfs/<папка реестра>
bash start.sh
```

Сервер слушает порт **39246** (конец командного диапазона, как рекомендует платформа). Открыть: в адресе своего Jupyter заменить всё после `/jserver` на `/proxy/39246/`, например
`https://…/datalabpro/jserver/lab/workspaces/auto-2` → `https://…/datalabpro/jserver/proxy/39246/`.
Скрипт идемпотентен: после перезапуска контейнера просто запустить снова. Пока порт занят реестром, другие сервисы его не получат.

### Участник команды: подключиться

Скопировать к себе папку реестра (нужны `app.py`, `connect.sh`, пакет `registry/`, `skills/`; fastapi для прокси не нужна) и выполнить:

```bash
bash connect.sh <табельный номер владельца>
```

Скрипт проверит, что реестр владельца отвечает, запустит прокси на порту 9000 и подскажет адрес: в адресе своего Jupyter заменить всё после `/jserver` на `/proxy/9000/`. Выберите себя в списке и введите свой PIN: PIN выдаёт владелец реестра в админ-панели. После перезагрузки страницы или перезапуска сервера нужно войти снова. Другой порт прокси: `PROXY_PORT=9001 bash connect.sh …`; другой порт реестра: `bash connect.sh <табельный> 39245`. Скрипт спросит логин и пароль BB — они нужны выгрузке карточек и базе знаний (Enter — без Bitbucket), см. «Выгрузка карточек знаний в BB».

Прокси пересылает серверу владельца только заголовки, нужные реестру (`X-Token`, `X-Session`, `X-User`, `Content-Type`, `Accept`, `Accept-Language`). Куки и `Authorization` браузера, в том числе куку JupyterHub сотрудника, он не пересылает, а `Set-Cookie` от сервера владельца не отдаёт браузеру: владелец реестра не получает вход в Jupyter коллеги.

## Вход, PIN и админ-панель

- **Сотрудники.** Каждый входит под своим ФИО и PIN (4–8 цифр). PIN задаёт и сбрасывает администратор; на сервере хранится только хеш с солью (PBKDF2-SHA256, 200 000 итераций): посмотреть PIN нельзя, только задать новый. После 5 неверных PIN подряд вход для этого ФИО блокируется на 5 минут. Сессия живёт 12 часов в памяти сервера; браузер хранит только её идентификатор в хранилище вкладки (sessionStorage, не localStorage): перезагрузка страницы вход не сбрасывает, а новая вкладка, закрытие вкладки, «Выйти» или перезапуск сервера — вход заново.
- **Запись только после входа.** Сохранение задачи, карточки знаний, удаление задачи и запросы к помощнику (лава-болл) работают только с действующей сессией; автор действия в истории — вошедший сотрудник. Чтение реестра (`GET /api/state`, команды `ctx`, `tasks`, `task`) работает без входа.
- **Что видно после входа.** В реестре и на доске сразу включён охват «Мои» (задачи, где сотрудник — исполнитель или замещающий); у тимлида — «Мой реестр» (его задачи как тимлида плюс свои как исполнителя). «Все» — весь реестр, переключение одним кликом. Охват не запоминается: при каждом входе — снова свой. Админ видит всё.
- **Администратор — владелец сервера.** `start.sh` при каждом запуске спрашивает админский PIN (дважды) и передаёт его серверу через stdin вместе с логином и паролем GP; PIN нигде не сохраняется. Войти как админ: на форме входа отметить «Войти как администратор».
- **Админ-панель** (видна только админу): люди (ФИО, email, цвет, команда, «активен»; «Задать PIN» / «Сбросить»), команды (название, тимлид, заместитель, состав; команду с задачами удалить нельзя), справочники (ЦК и роли, блоки, матрица, события, регулярности — раньше вкладка «Справочники»). Неактивный сотрудник не может войти, его сессии закрываются. Переименование сбрасывает PIN. Любую задачу администратор правит в её карточке, включая статус; в истории — «Правка администратором: …».
- **Локальный запуск для разработки:** `python3 app.py --local --no-browser --port 39299` — вход админа выключен; с админом: `printf '1234\n' | python3 app.py --local --no-browser --port 39299 --admin-pin-stdin`.

## registry.env — только несекретное, всё необязательно

```bash
REG_STORAGE=json                 # json | gp | sqlite — переключатель хранилища
GP_HOST=...                      # для REG_STORAGE=gp
GP_PORT=5432
GP_DATABASE=...
GP_SCHEMA=...
GIGACHAT_MODEL=Qwen3.5-397b      # по умолчанию
REG_PORT=39246                   # порт реестра (для команды — 39235–39246)
REG_TAB_NUMBER=...               # ваш табельный — только чтобы start.sh напечатал готовую команду для коллег
REG_LOCAL_HOST_CHECK=1           # --local: принимать только localhost (0 — отключить проверку Host)
REG_AI_FILE_MAX_MB=10            # файлы в помощнике: размер одного файла
REG_AI_FILE_MAX_CHARS=50000      # текст одного файла, длиннее — обрезается
REG_AI_FILES_MAX_CHARS=100000    # текст всех файлов диалога в запросе к модели и в истории
# REG_BB_* — выгрузка карточек знаний в BB, см. раздел «Выгрузка карточек знаний в BB»
```

Адрес шлюза моделей DataLab Pro задан по умолчанию (`GIGACHAT_API_URL` из инструкции платформы); переопределять не нужно. Файл читают `app.py`, `start.sh` и `connect.sh`; логин, пароль или токен в нём — ошибка запуска. Скрипты читают файл как bash: значение с пробелами берите в кавычки (`REG_KB_REPO_URL="/home/jovyan/мои файлы/repo.git"`).

## Этапы задачи и права

Порядок: **Новая → В работе → На согласовании (⇄ На доработке) → Согласована → Завершена → Принята.** Каждый видит в карточке только доступные ему кнопки; поля, которые ему сейчас нельзя менять, показаны только для чтения (пунктирная рамка). Права проверяет сервер: при нарушении — ошибка 403 с понятным текстом.

- **Команды** (T-007): справочник `teams: [{id, name, lead, deputy}]`, у человека `team` — id команды, у задачи — поле `team`. Роль «тимлид» не задаётся вручную: её получают лид и заместитель команды, права у них одинаковые. Справочник без команд (до T-007) при чтении превращается в команды по прежним тимлидам; старые задачи получают команду по полю «Тимлид».
- **Тимлид задачи** (лид или заместитель команды задачи; в поле «Тимлид» — тот, кто поставил, ему идут письма «тимлиду»): ставит задачу и правит постановку, пока она «Новая»; на согласовании решает, сохранять ли результат в БЗ, и «Согласовать» (при «БЗ — нет» задача сразу «Завершена») или «Вернуть на доработку» с комментарием и новым сроком; в «Завершена» проверяет БЗ и «Принять» или «Вернуть» (к базе знаний или на доработку результата). У регулярных — «Обратная связь» и «Начать новый цикл» (после «Принята»).
- **Исполнитель и замещающий** (равноправны): «Взять в работу»; блок «Результат» и «Отправить на согласование» в «В работе» и «На доработке»; в «Согласована» — карточки знаний и факт размещения, затем «Завершить» (нужна хотя бы одна карточка или отметка о размещении).
- **Ставить задачи** могут лид и заместитель команды (тимлидом задачи становится автор, команда — его; если команд несколько — выбрать, в API `params.team`) и администратор. Обязательны название, исполнитель и срок (у регулярной — регулярность).
- **Администратор** правит любую задачу и любое поле, включая статус; только он удаляет задачи. «Принята» закрыта для всех, кроме администратора.
- **Письма** («Написать письмо»): постановка, на согласование, на доработку, «Согласована» (исполнителю), «Завершена» (тимлиду: база знаний готова), «Принята» (руководителю ЦК), «Сформировать карточку(ки)» (ответственному за БЗ, только из меню).
- **API:** `/api/login` и `/api/whoami` отдают у пользователя `lead_teams` — id команд, где он лид или зам. `POST /api/task` принимает `action_code` — `create`, `edit`, `take`, `to_review`, `approve`, `rework`, `finish`, `accept`, `return`, `new_cycle`, `feedback` — и `params` (`rework`: comment, deadline; `return`: to = approved | rework, comment, deadline; `new_cycle`: deadline; `feedback`: text). Новый статус и служебные поля (история, итерации, циклы, обратная связь, даты) выставляет сервер; клиентские значения этих полей игнорируются.

## Выгрузка карточек знаний в BB

В «Согласована» исполнитель или замещающий (и админ) выгружает карточки знаний задачи в репозиторий базы знаний в Bitbucket: раздел «База знаний» → «Выгрузить карточки в BB». Получается новая ветка `kb/<once|regular>-<номер>-<ГГГГММДД-ЧЧММСС>` с файлами карточек в папке `KB/` (файл — как в реестре: `# вопрос`, пустая строка, ответ) и pull request в целевую ветку — от имени сотрудника, с его учёткой BB. Ссылка на PR записывается в задачу: список «Выгрузки в BB» (виден всем, кто открыл задачу), история, «Факт размещения карточки» (пустой — заполняется, иначе ссылка дописывается). Повторная выгрузка — новая ветка и новый PR; если в BB карточки уже такие же — «выгружать нечего», PR не создаётся.

```
браузер сотрудника → его Jupyter /proxy/9000/ → его прокси (connect.sh, его контейнер)
  ├─ остальные запросы /api/* ──────────→ сервер реестра владельца (как раньше)
  └─ /api/bb/status, /api/bb/upload — обрабатывает сам прокси:
       1. сервер реестра по сессии сотрудника: права, карточки, настройки репозитория (/api/bb/task)
       2. git в контейнере сотрудника, с его учёткой: постоянный клон → ветка → KB/*.md → commit → push
       3. pull request — напрямую через REST API Bitbucket (Basic-авторизация)
       4. серверу реестра — только результат (/api/bb/done): ссылка на PR, ветка, файлы
```

- **Без MCP.** Реестр работает с Bitbucket напрямую: git (клон/коммит/push) и REST API (pull request). Ваш `server.py` (MCP-сервер) реестру больше не нужен.
- **Учётка BB — только у сотрудника, только в памяти.** Сервер реестра в BB не ходит; учётки владельца (GP, админский PIN) к сотруднику не попадают. `connect.sh` спрашивает логин и пароль BB при каждом запуске (Enter — без Bitbucket) и передаёт прокси через канал на stdin (`--bb-creds-stdin`). Прокси отдаёт их git через askpass-помощник — статический скрипт без секретов читает учётку из канала в памяти ядра; REST-запрос — заголовок Authorization. В файлах, аргументах команд и окружении процессов (`/proc/<pid>/environ`) учётки нет.
- **Постоянный клон** (`REG_BB_CLONE`, по умолчанию `~/bb`): при запуске прокси проверяется и клонируется/обновляется (fetch + сброс на `origin/<ветка>`), между выгрузками переиспользуется; сбой push/PR — клон переклонируется и выгрузка повторяется один раз. Клон — чистый кэш: локальных правок в нём не бывает.
- **Владелец выгружает так же — через свой прокси:** `bash connect.sh 127.0.0.1:39246`, затем открыть `/proxy/9000/`. Через `/proxy/39246/` кнопка неактивна и объясняет, как открыть реестр через прокси.
- **Сторона сотрудника серверу реестра не доверяет:** репозиторий принимается, только если это локальный путь (тесты) или хост `REG_BB_BASE_URL` сотрудника и в адресе нет логина; папка, имена файлов, проект, репозиторий и ветка проверяются; файлы пишутся только внутри клона, без перехода по символическим ссылкам.
- **Ошибки** — по-русски, с шагом и подсказкой («BB, шаг «push»: … Что сделать: …»), без учётки; при ошибке в задачу ничего не пишется. На одном прокси — одна выгрузка за раз. В контейнере сотрудника нужны `git` и git-идентичность (`git config --global user.name` и `user.email`).

Настройки — в `registry.env`, несекретные:

| Кто задаёт | Настройка | Что это |
|---|---|---|
| владелец | `REG_BB_REPO_URL` | адрес клонирования репозитория БЗ: http(s), без логина |
| владелец | `REG_BB_PROJECT` | ключ проекта для pull request |
| владелец | `REG_BB_REPO` | slug репозитория |
| владелец | `REG_BB_BRANCH` | целевая ветка pull request, по умолчанию `master` |
| владелец | `REG_BB_DIR` | папка карточек в репозитории, по умолчанию `KB` |
| сотрудник | `REG_BB_BASE_URL` | корпоративный Bitbucket (REST и проверка хоста), по умолчанию `https://df-bitbucket.ca.sbrf.ru` |
| сотрудник | `REG_BB_TIMEOUT` | предел одной операции (git/REST), секунд, по умолчанию 600 |
| сотрудник | `REG_BB_CLONE` | путь постоянного клона, по умолчанию `~/bb` |

**API:**
- `GET /api/bb/status` — на сервере реестра: `{"available": false, "server_configured", "reason", "missing": [<недостающие REG_BB_*>], "target"}` (`target` — если настроено); на прокси сотрудника: `{"available", "reason", "via": "proxy", "server_configured", "target"}`.
- `POST /api/bb/upload {"kind", "id"}` — только на прокси сотрудника → `{"pr_url", "pr_id", "branch", "files", "task"}`; ошибки — 400/403/409 с `error` (у ошибок BB ещё `step`). Прямо на сервере реестра — 400 «через свой прокси».
- `GET /api/bb/task?kind=&id=` — с сессией (иначе 401); исполнитель или замещающий (или админ), задача «Согласована», есть карточки, у владельца настроен репозиторий — иначе 403/400 по-русски → `{"task": {"kind", "id", "title"}, "cards": [{"file", "title", "body"}], "target": {"repo_url", "project", "repo", "branch", "dir"}, "by"}`.
- `POST /api/bb/done {"kind", "id", "pr_url", "pr_id", "branch", "files"}` — с сессией, те же права; атомарно пишет в задачу `bb: [{ts, by, pr_url, pr_id, branch, files}]`, запись в историю «Карточки выгружены в BB: pull request №N» и `bz_card` → `{"task"}`. `pr_url` — только http(s).

## Базы знаний (T-012)

База знаний — **один** git-репозиторий; онтология — его папки и подпапки (не с точки); адрес и ветка — в настройках владельца (`REG_KB_REPO_URL`, `REG_KB_BRANCH`). Создания и выбора баз нет: в окне карточки — селектор **узла онтологии** (дерево подгружается сам) и кнопка «Отправить в репозиторий». Узел онтологии — папка: карточка уезжает в `<узел>/<имя файла реестра>`, у неё в реестре появляется ссылка на файл в Bitbucket. Отправка — через pull request (REST API), из контейнера сотрудника с его учёткой BB; кнопка дополняет выгрузку всех карточек задачи из раздела «База знаний». Права — те же: исполнитель или замещающий в «Согласована» (админ — всегда).

```
# Онтология — фактические папки и подпапки репозитория БЗ (не начинающиеся на точку).
# Дропдаун строится обходом клона; ontology.yml больше не нужен.
KB-репозиторий/
├── Общие вопросы/            ← узел
│   └── 1_Как получить доступ.md   ← карточка
└── Аудит моделей/            ← узел
    └── Метрики качества/     ← узел-подпапка
```

- **Постоянный клон у сотрудника** (`REG_KB_CLONE`, по умолчанию `~/kb`): при запуске прокси проверяется и клонируется/обновляется; онтология — обход папок клона (скрытые папки и симлинки — не узлы). Отправка проверяет, что выбранный узел существует в дереве. Сбой push/PR — клон переклонируется, отправка повторяется один раз; «в БЗ уже лежит без изменений» — точный ответ без повторов.
- **Модель карточки.** `task.cards[]` — объекты `{path, bb?}`; `bb` — результат отправки: `{ts, by, node, file_url, pr_url, pr_id}`. Старые записи (строки-пути) читаются совместимо, на диске не мигрируются. `cards` — служебное поле: подделать `bb` через `/api/task` нельзя.
- **Стороны не доверяют друг другу**: сервер проверяет права, цель и узел (относительный путь без «..» и скрытых сегментов), прокси проверяет ответ сервера (хост — только свой корпоративный Bitbucket или локальный путь, без логина в адресе; карточка и узел совпадают) и дерево папок (форма, пути, предел узлов).
- **Git не хранит пустые папки**: узел появляется в онтологии, только когда в папке есть хотя бы один файл (`.gitkeep` или первая карточка) — задокументированное ограничение git.

Настройки — в `registry.env`, несекретные:

| Кто задаёт | Настройка | Что это |
|---|---|---|
| владелец | `REG_KB_REPO_URL` | адрес клонирования единственной БЗ: http(s), без логина |
| владелец | `REG_KB_BRANCH` | ветка БЗ, по умолчанию `master` |
| сотрудник | `REG_KB_CLONE` | путь постоянного клона, по умолчанию `~/kb` |

`REG_KB_*` и `REG_BB_*` независимы: указать их на один репозиторий или разные — решает владелец значением.

**API:**
- `GET /api/kb/status` — на сервере: `{available: false, via: proxy, configured, reason, target: {repo_url, branch}}` (`target` — если настроено); на прокси: `{available, reason, via: proxy, configured, target}`.
- `GET /api/kb/ontology` — только на прокси, без параметров (БЗ одна) → `{nodes: [{name, path, children}]}`.
- `GET /api/kb/task?kind=&id=&path=&node=` — с сессией; исполнитель или замещающий (или админ), задача «Согласована», карточка в задаче, узел — валидный путь → `{task, card: {path, title, body}, target: {repo_url, branch, node}, by}`.
- `POST /api/kb/upload {kind, id, path, node}` — только на прокси → `{file_url, pr_url, pr_id, task}`; ошибки — 400/403/409 с `error` (у ошибок BB ещё `step`). Прямо на сервере реестра — 400 «через свой прокси».
- `POST /api/kb/done {kind, id, path, node, file_url, pr_url, pr_id}` — с сессией, те же права; атомарно пишет `bb` в карточку и запись в историю «Карточка отправлена в базу знаний: узел «…», pull request №N» → `{task}`. Ссылки — только http(s).

## Хранилище: переключатель

| `REG_STORAGE` | Куда пишется | Когда |
|---|---|---|
| `json` (по умолчанию) | локальные JSON в `data/` | запись в БД выключена |
| `gp` | Greenplum, таблицы `<GP_SCHEMA>.ck_registry_tasks / _config / _cards` | рабочий режим |
| `sqlite` | `registry.db` | отладка схемы |

Переключение — поменять `REG_STORAGE` и перезапустить `bash start.sh`. Данные между хранилищами не синхронизируются сами; перенести всё разом:

```bash
python app.py copy-to gp --storage json      # из локальных JSON в GP (спросит логин/пароль GP)
python app.py copy-to json --storage gp      # обратно, например для резервной копии
```

Перенос сохраняет номера задач, версии и карточки; в непустое хранилище без `--force` не пишет.

### Greenplum

- Подключение — как в корпоративном шаблоне: `asyncpg`, одно соединение, перед подключением продление Kerberos-тикета (`kinit -R`). Нужен `pip install asyncpg` из зеркала PyPI; в режиме `json` зависимость не нужна.
- **Логин и пароль GP нигде не хранятся.** `start.sh` спрашивает их при каждом запуске и передаёт серверу через канал на stdin — не через файл и не через переменные окружения (окружение процесса читается из `/proc/<pid>/environ`). Пароль можно оставить пустым, если вход по Kerberos. Формат stdin `app.py`: логин GP, пароль GP (с `--creds-stdin`), затем админский PIN (с `--admin-pin-stdin`) — по строке.
- Таблицы создаются сами при первом запуске. Если у учётки нет прав на CREATE, DDL можно выполнить отдельно или отдать DBA: `python app.py ddl`.
- Каждая задача — строка с JSON-документом и номером версии. Правка проверяет версию атомарно (`UPDATE … WHERE v = …`), поэтому несколько тимлидов со своими серверами на одной базе не затирают друг друга; одновременное создание задач получает разные номера.
- Проверить подключение: `python app.py check --storage gp`.

## Свои данные: как не писать в общую базу

- **Локальные JSON** — свой реестр в папке, запись в БД выключена: `python3 app.py --storage json --port 39246`
  (папка — `REG_JSON_DIR`, по умолчанию `./data`); через start.sh: `REG_STORAGE=json bash start.sh` —
  переменные окружения важнее `registry.env`.
- **Своя песочница в промышленном GP** — тот же Greenplum, но изолированные таблицы:
  `GP_SCHEMA=своя_схема python3 app.py …` или свой префикс таблиц `REG_TABLE_PREFIX=моё_`. Общие таблицы
  не затрагиваются; удобно проверять настоящее поведение GP.
- **Перенос данных** между хранилищами: `python3 app.py copy-to …`.
- `--local` про хранилище не говорит — только про адрес: бинд 127.0.0.1, открытие браузера и проверка
  Host (принимать только localhost; отключается `REG_LOCAL_HOST_CHECK=0` — например, когда `--local`
  пробрасывается через локальный прокси с чужим заголовком Host). На DataLab запускайте без `--local`.

## Ассистент: веб-чат и GigaCode с одними скиллами

Скилл — папка `skills/<имя>/SKILL.md` (frontmatter `name`, `title`, `description` + текст). Необязательные поля frontmatter (T-008): `roles` — кому доступен, через запятую: `teamlead` (лид, зам и админ), `employee`, `admin`; без поля — всем; `greeting` — приветствие в пустом чате; `examples` — примеры запросов через ` | `; `placeholder` — подсказка в поле ввода.

Скиллы в комплекте:
- **«Постановка задачи»** (`postanovka`, `roles: teamlead`) — карточка задачи по регламенту, кнопка «Создать задачу из карточки» (блок ```task```).
- **«Результат и карточка знаний»** (`rezultat`, всем) — человек называет номер задачи, помощник сверяет по контексту, что он исполнитель или замещающий, и по статусу: «В работе» / «На доработке» — формулирует результат, кнопка «Перенести результат в задачу N» открывает задачу с заполненными полями (блок ```result {"kind","id","result_desc","result"}```), отправляет на согласование сам человек; «Согласована» — собирает карточку знаний (вопрос и ответ), кнопка «Прикрепить карточку к задаче N» сохраняет её (блок ```card {"kind","id","title","body"}```, `POST /api/card`); в других статусах объясняет, что дальше. Если человек не исполнитель/замещающий или статус не тот — кнопка неактивна с пояснением; права ещё раз проверяет сервер.

Доступ и контекст: `GET /api/llm` с сессией отдаёт только доступные скиллы (с `greeting`, `examples`, `placeholder`, `roles`) и `default` по роли — лиду, заму и админу «Постановка задачи», сотруднику `REG_DEFAULT_SKILL_EMPLOYEE` (по умолчанию `rezultat`); без сессии — только скиллы без `roles`. `POST /api/llm` с недоступным скиллом — 403, с неизвестным — 400, до модели запрос не доходит. В контекст модели (оба движка) добавляется, кто пишет (ФИО; лид, зам какой команды или сотрудник) и его задачи (номер, вид, название, статус, его роль; до 50, принятые — за 30 дней); исполнителю в рабочих статусах — описание, текущий результат и замечание тимлида. Положите сюда же свои скиллы GigaCode — веб подхватит их после перезапуска, в чате появится выбор скилла. Если GigaCode держит скиллы в другой папке, укажите её в `REG_SKILLS_DIR`, и веб будет читать ровно те же файлы.

**Веб-чат (лава-болл)** отправляет текст SKILL.md системным промптом в `GIGACHAT_API_URL/chat/completions` и дописывает контекст реестра: блоки направлений, события, дату, кто пишет и его задачи. Заголовок `Authorization` на Pro не нужен; если шлюз его потребует — `GIGACHAT_API_TOKEN` в окружении. В API-режиме модель видит только текст SKILL.md: скрипты и файлы из папки скилла работают только в GigaCode.

**История лава-болла — у каждого своя, на сервере.** Диалог (последние 40 сообщений) и «История запросов» (последние 30 запросов без повторов) хранятся в реестре по ФИО вошедшего: json — файл `ai_history.json`, sqlite и GP — таблица `ai_history` (в GP — `DISTRIBUTED BY (person)`). С другого компьютера сотрудник видит свой диалог, другой сотрудник его не видит; в браузере история не хранится. Кнопка с часами в шапке помощника открывает прошлые запросы: клик подставляет текст в поле ввода, не отправляя. Команда копирования хранилищ историю не переносит.
- `GET /api/ai/history` → `{"msgs": [{"role", "content"}], "queries": ["…"]}` — только своё, без сессии 401;
- `POST /api/ai/history {"action": "reset"}` — новый диалог (запросы остаются), `{"action": "clear_queries"}` — очистить запросы; ответ как у GET;
- `POST /api/llm` после удачного ответа сам сохраняет диалог и запрос; при ошибке модели ничего не сохраняется.

**Файлы в помощнике (T-009).** Скрепка у поля ввода или перетаскивание в окно помощника: .docx и .txt, до 5 файлов к сообщению; сообщение можно отправить и без текста. Текст извлекает сервер реестра на стандартной библиотеке, в памяти — на диск файлы не пишутся: .docx — абзацы, списки («- »), таблицы (ячейки через « | »); .txt — UTF-8 (с BOM и без), UTF-16/UTF-32 с BOM, иначе cp1251. Старый .doc и PDF не поддерживаются — ошибка с подсказкой сохранить как .docx. Отклоняются повреждённые файлы, zip-бомбы, XML с DOCTYPE/ENTITY и слишком глубокой вложенностью.
- Модель (оба движка) получает текст файлов перед текстом сообщения, в разметке `[Файл «имя»]` … `[Конец файла «имя»]`; в пузыре сообщения — только имена файлов. Файлы остаются в контексте диалога и хранятся в его истории на сервере; «Новый диалог» убирает и их.
- Лимиты (registry.env): `REG_AI_FILE_MAX_MB` — размер файла (10 МБ); `REG_AI_FILE_MAX_CHARS` — текст одного файла (50 000 символов), длиннее — обрезается с пометкой; `REG_AI_FILES_MAX_CHARS` — текст всех файлов диалога в запросе к модели и в сохранённой истории (100 000), считая от новых сообщений к старым; файл, который не влез, остаётся с именем и пометкой «текст не передаётся». Лимиты применяет сервер, клиенту не доверяет.
- `POST /api/ai/file {"name", "data": "<base64>"}` → `{"name", "text", "chars", "truncated"}` — только с сессией (иначе 401); `chars` — длина всего извлечённого текста, `text` уже обрезан до лимита; ошибки — 400 с текстом по-русски.
- `POST /api/llm`: у сообщений пользователя необязательное `files: [{"name", "text", "truncated"}]`; `content` может быть пустым, если есть файлы; больше 5 файлов в сообщении — 400. В ответе добавилось `msgs` — диалог в том виде, как он сохранён на сервере (с учётом лимитов). `GET /api/llm` отдаёт `file_limits` — лимиты для клиента.
- `GET /api/ai/history`: у сообщений с файлами — `files`; у файла, который не влез в общий лимит, — `{"name", "truncated", "dropped": true}` без текста.

**GigaCode в лава-болле.** В шапке чата переключатель «через API / через GigaCode». В режиме GigaCode сервер реестра на каждое сообщение запускает `gigacode -p` в папке реестра и передаёт ему через stdin контекст реестра, текст выбранного скилла и всю историю диалога с подписями по роли пишущего — «Сотрудник (ФИО)», «Тимлид (ФИО)», «Заместитель тимлида (ФИО)», «Администратор реестра» (без `--continue`: при нескольких пользователях сессии бы перемешались). Запуски идут по одному, остальные ждут.
- Права: `--approval-mode default`. В неинтерактивном режиме подтверждать некому, поэтому shell-команды и правка файлов агенту недоступны — он читает и отвечает; задачу из его карточки тимлид создаёт кнопкой, как и в режиме API. `auto-edit` запрещён: иначе любой участник команды через чат мог бы заставить агента править файлы на сервере владельца.
- Запросы выполняются под учёткой владельца сервера и расходуют его лимиты GigaCode.
- Настройки (необязательно): `REG_GIGACODE_BIN` (по умолчанию `gigacode`), `REG_GIGACODE_MODEL`, `REG_GIGACODE_APPROVAL` (`default` или `plan`), `REG_GIGACODE_TIMEOUT` (600 с).
- Если GigaCode на сервере не найден, пункт в переключателе неактивен.

**GigaCode в терминале** работает с реестром через сервер — у него уже есть подключение к хранилищу, в том числе к GP. Настраивать вручную ничего не нужно: `start.sh` (и `connect.sh` у коллег) прописывает в `~/.bashrc` путь `CK_REGISTRY`, а у коллег ещё и `REG_SERVER` — адрес общего сервера. Достаточно открыть новый терминал и запустить GigaCode; скилл сам вызывает

```bash
python "$CK_REGISTRY/app.py" ctx                         # блоки, люди, команды, роли, события, дата
python "$CK_REGISTRY/app.py" tasks [--status Новая] [--person "ФИО"]
python "$CK_REGISTRY/app.py" task once 12
python "$CK_REGISTRY/app.py" create-task card.json --by "ФИО тимлида или зама" [--team КОМАНДА]
```

Команды получают ключ API со страницы сервера так же, как браузер; на диск ничего не пишется. `ctx`, `tasks`, `task` работают без PIN. `create-task` спрашивает PIN тимлида в терминале (`--by` — ФИО лида или заместителя команды; если он руководит несколькими командами — `--team` с id или названием). `ctx` показывает команды с лидом, замом и составом. Если терминала нет (лава-болл, неинтерактивный запуск), команда отказывает: задачу создают через веб-форму («Новая задача» или «Создать задачу из карточки» в помощнике).

## Интерфейс

`templates/index.html` + `static/` — интерфейс без сборки и CDN: каркас (Jinja2, сервер подставляет ключ API) и ES-модули `static/js/` (вход — `main.js`), стили — `static/css/` в порядке загрузки. Окно помощника перетаскивается за шапку и меняет размер за правый нижний угол, шар тоже перетаскивается; положение и размер запоминаются в браузере, двойной клик по шапке окна возвращает его на место. «Написать письмо» в карточке задачи открывает меню из семи писем регламента, письмо по текущему этапу — первым. Анимации работают и при системной настройке «уменьшить движение» (в VDI она часто включена).

Кроме того: выбор скилла в чате ассистента, метка хранилища в шапке, «Обновить» вместо «Синхронизировать», «Журнал» из истории действий по задачам (git больше нет). Адрес реестра открывается и с `/` на конце, и без.

Если у вас своя доработанная версия интерфейса, перенесите в неё:
1. базовый путь API: `const BASE = (p => p.endsWith('/') ? p : /\.html?$/.test(p) ? p.replace(/[^/]*$/, '') : p + '/')(location.pathname);` — без этого адрес `…/proxy/39246` (без слеша) ломает все запросы;
2. выбор скилла: `<select id="aiSkill">` из `GET /api/llm` с заголовком `X-Session` (`skills`, `default`) и `skill` в `POST /api/llm`;
3. запись — с заголовком `X-Session` (сессия из `POST /api/login`, в памяти JS и в sessionStorage вкладки, T-005); на ответ 401 с `login: true` показать форму входа. `X-User` больше не используется.

source .venv/bin/activate                                   # Python 3.12
